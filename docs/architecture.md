```text
State assessment platform authorised exports/APIs ─────┼─> Source adapters
PARAKH published aggregates ────────────────────────────┤       |

                                     |                        |                  |
                                     +------------+-----------+------------------+
                                                  v
                                      Explainable triage engine
                                   (reading / numeracy / attendance)
                                                  |
                                Teacher action queue + intervention log
                                                  |

                                                  |

```

## Prototype implementation
- Browser SPA calls FastAPI over JSON/CSV HTTP endpoints.
- FastAPI validates request models and enforces demo role boundaries.
- SQLite stores schools, users, learners, assessments, interventions, imports and audit logs.
- CSV import validates required columns and known school IDs, then upserts by pseudonymous learner ID.
- `/api/governance` exposes canonical schema and source mapping.
- `/api/docs` is generated by FastAPI at `/docs`.

## Production target

For deployment, use a React/Next.js or equivalent frontend if the team needs a larger component system; FastAPI services behind an API gateway; PostgreSQL with row-level security; object storage for immutable source files; a queue for asynchronous ingestion; OIDC identity; and observability. The hackathon build intentionally keeps the stack lightweight and reproducible.

## Product upgrade notes (prototype boundary)

The current executable API remains SQLite-backed for frictionless judging. A PostgreSQL target DDL is supplied at `backend/migrations/001_postgresql_schema.sql`; this is a reviewed migration starting point, not a claim that the runtime has been switched to PostgreSQL. The API now issues signed HS256 JWTs with expiry, issuer and audience validation. OIDC federation (e.g. state SSO) remains a deployment integration.

New capabilities include longitudinal reassessment, progress history, administrative school/block aggregate tiles, a transparent early-warning heuristic, DIKSHA resource discovery links and idempotent offline event-metadata sync. Offline queued events are not automatically applied as learner mutations: conflict review and teacher confirmation are required. The current map view intentionally avoids fabricated geocoordinates; authoritative UDISE+ coordinates and boundary licensing are prerequisites for a real map.

## Demo data expansion (v3.1)
The local seed generator creates 30 synthetic schools across 10 demonstration blocks, 440 learners, two domain observations per learner at two illustrative timepoints for the expanded panel, and intervention examples. This data exists only to exercise filtering, cohort aggregation, risk ranking and longitudinal UI states. It is not sourced from UDISE+, ASER or PARAKH.

## Analytics pipeline
1. Validate incoming score and attendance ranges and preserve source labels.
2. Map reading/numeracy to the canonical domains.
3. Compute transparent learner-level risk heuristic for human review.
4. Aggregate by block × grade for administrative prioritisation.
5. Compare earliest and latest observations for descriptive progress signals.
6. Present teacher action suggestions and reassessment prompts; no automated high-stakes decisions.
